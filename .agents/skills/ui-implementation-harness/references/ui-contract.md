# UI契約：実装と移行の索引

意味・意図・密度・視覚表現はUI Design、全体アーキテクチャ・認可・一般品質は
アプリ側、UI内の構成・状態・操作・接続はUI実装担当が所有する。
既存正本を参照し、不足する実装情報だけを機能単位で記録する。

## 必要になる情報

| 項目 | 記録する内容 |
| --- | --- |
| 同一性 | 機能ID、要件ID、Designの固定改訂または合意済み事項と未確定点 |
| 部品とコンテナ | 安定ID、意味・役割、配置・slot、コード位置。画面階層とファイル階層は別 |
| 操作 | 意味ID、全入口、対象引数、前提、成功・失敗・取消、起動先、実処理接続 |
| 状態 | 所有者、画面/機能等のスコープ、読み手・更新者、遷移、破棄・再開、派生値 |
| 境界 | 独立した認可・検証・監査・障害処理を参照し、別処理として保持 |
| デザイン | トークン、表示状態、focusとアクセシビリティ条件への参照 |
| 接続状態 | 接続ごとにmock/partial/unimplemented/productionと実装位置・未検証範囲 |
| 受入 | 必要な操作・状態遷移・接続・ケースと、既存checkへの対応 |

局所的で自明なDOM要素をすべて台帳化しない。外観のみの小変更は既存契約と差分への参照でよい。
コード参照、型、既存テストを証拠とし、契約は意味と横断依存を見つける索引にする。

## 親子以外の関係

`contains`（コンテナ→子）、`uses`（利用側→共通部品）、`invokes`（入口→操作）、
`reads/writes`（利用側→状態）、`publishes/subscribes`（発行・購読側→イベント）、
`opens`（操作→画面）、`calls`（操作→実処理）、`styles`（部品→デザイン定義）を区別する。
共有操作・共有状態・イベント・外部接続・独立境界は追跡する。
イベントはpayload、発行条件、購読範囲、解除条件を明確にする。

状態の正本は一つの所有者に置く。編集バッファ・キャッシュ・楽観的更新は
目的、同期方向、競合・失敗時の回復を記録する。共有フローでも画面インスタンスの状態は分けられる。

## 一つの追加フローの例

Toolbar/Tree/ContextMenu → `operation.task-add` → `dialog.task-add` → 作成アダプター。
入口は`projectId`、必要なら`parentTaskId`、`source`、focus復帰先を渡す。
右クリック対象P2は選択中P1と別に固定し、後からglobal選択値で上書きしない。
`source`やUIの`canEdit`は認可の証明ではない。

`closed → editing → submitting → closed`、失敗は`submitting → editing(error)`。
送信前の取消は処理を呼ばない。送信後は応答抑制・通信取消・サーバー処理の撤回を区別し、
取消が保存撤回を保証するとはしない。要求ID・世代等で遅い応答の反映先を限定する。

通常設定と権限管理はTextField/FormLayout等を共有しても、保存・認可・検証・監査は別の契約へ接続する。
Provider、汎用イベントバス、多数のbooleanによる統合は必要性を確認してから選ぶ。

## HTMLモックからの継承

HTML/CSS/JSは論理的な役割を区別するが、別ファイル化は必須ではない。
Sitesは対象環境の実際の生成・編集・保存・ソース取得とQA制約を確認し、最小構成を選ぶ。
移行時は改訂を固定し、意味ID・UI階層・コンテナ・操作・遷移・デザイン・接続状態を
対象技術へ対応づける。同じ成功・失敗・取消ケースを再使用し、HTMLの逐語移植は要求しない。
モックで未実装の保存・認可・監査・OS連携は対象環境で接続・検証してから完了とする。

## 検証との接続

期待する振る舞いと検証対象は要件・確定Designから設計時に固定し、実装と独立レビューで照合する。
必要なケースの未実行は未完了、実装されない接続は未実装とする。宣言やJSONの形式だけでは実動作を証明しない。
段階1の例は説明用の契約であり、必須JSON schemaや自動ゲートではない。
将来の検査を追加するときも既存工程の証跡・鮮度管理を再利用する。
