# 共通工程の進行

プロジェクトルートでAGENTS指示、`.harness/rules.md`、`.harness/protocol.md`、`.harness/project.json`を読む。
0.2.0の標準の全体進行はpoteto-mode。このスキルは共通工程の案内として使い、project.jsonのorchestratorがpoteto-modeならそのSKILL.mdを読み、接続規約に従って専門スキルへ進む。相互に呼び戻して入口をループさせない。
導入済みでなければ、共通リポジトリの `scripts/install.py --project <root>` が必要であると説明する。プラグイン導入だけでランタイム配置済みとは判断しない。

1. ユーザーの依頼に合う変更単位を見つけ、`python3 .harness/harness.py status <id>` で現在地を確認する。新しい依頼は `new <id> --kind new|change --author <作業者ID> --context <セッションID>` で開始する。
2. discoveryでは実際のリポジトリ、依頼、既存挙動を調べる。目的を変える未解決質問は確認し、回答済み事項を質問し直さない。
3. project.jsonのskill_bindingsから、その工程の利用可能なスキルを使う。未確認の外部スキルは実行した扱いにせず、接続状況を明示する。
4. 現在の `<phase>.json` を実際の判断と根拠で埋める。作業ログは成果物の代わりにしない。
5. `advance <id>` を実行し、成功したら次の工程へ進む。失敗は同じ工程で修正する。上流変更は `reopen <id> <phase> --reason <理由>` を使う。
6. implementationは、実装と意味のある検証コマンドを用意し、`run <id>` を実行して成功証跡を得る。
7. reviewはホストが許す新しいコンテキストへ自動委譲する。要件・設計・差分と実スキルのパスを渡し、実装の会話履歴を複製しない。委譲できない場合は別の作業者・別コンテキストへ引き継ぐ。現在の実装セッションでレビュアー名だけを変えて独立レビューを装わない。別セッションの開始やレビューが必要なら、完了した成果物と未完了条件を明確に伝える。
8. done後はrules.mdの自律配送に従い、autonomyが指定するreview/pr/mergedまで継続する。自律配送ではreview.jsonにマージ先のbase_shaを記録し、ship-checkで確認する。接続GitHubツールを優先し、未提供なら認証済みghでshipを一回ずつ実行する。CI待機は完了とせず、delivery.jsonと実PRを照合して再開する。最終回答は結果・検証・PRリンクを短い自然な日本語で示す。

ユーザーが許可した作業は継続する。工程の区切りだけを理由に再承認を求めない。外部公開・サービス変更の許可はユーザーと実行環境の指示に従う。
