# 設計と実装

AGENTS、protocol、対象変更のdiscovery.json、requirements.json、state.jsonを読む。
既存の構成とコーディング規約を調べ、依頼を満たす最小の方針をdesign.jsonへ記載する。
protocol.mdの「原指示と目的の契約」でrequestとsourcesを読み、実在する仕様・API・ライブラリ・既存関数を確認する。責務・データ・状態・依存・変更対象と動作確認を既存approach・decisions・traceabilityへ具体化する。問題の理解に必要な抽象化を、コードの抽象層追加と混同しない。
既存資産の再利用→最小拡張→既存責務への追加→必要な新設の順で選ぶ。既存関数の小修正で足りればそれを選び、候補手段だけを理由に汎用化しない。見た目の変更ではイベント・業務処理を保つ。
不動作は既存仕様・再現・原因を先に調べ、基本機能・技術・前提の見落としを確認してから修正する。利用可能なら既存の根本原因調査担当を使い、同じ調査工程を重ねない。迂回処理や追加APIで症状を隠さない。
構造検査が有効ならstructural-quality.mdに従い、実装前baseline、再利用候補の採否、affected_pathsとnew_module_reasonsを既存成果物へ記録する。意味的な重複、責務、最小変更を検討し、検査を通すためだけの分割・迂回を追加しない。
影響範囲、判断理由、実際に使える回復手順を示す。

全要件IDをtraceabilityで変更予定パスと検証IDに対応づける。
検証コマンドはproject.jsonのchecksにargv配列とタイムアウトで登録する。
既存のテスト・lintを使い、受入条件を直接確認できない場合は適切な検証を追加する。
意味のない成功コマンドや、実装をそのままなぞる検証で受入条件を代用しない。

設計のadvanceに成功したら実装を行う。
implementation.jsonへ作業者ID、変更パス、要約、実際の制約を記録する。
設計範囲を変える場合はreopenで上流へ戻る。
自動修正は検証前に行い、runには修正を伴わないコマンドを登録する。
`python3 .harness/harness.py run <id>` の観測結果を使い、失敗は修正して再実行する。
成功後のadvanceでreviewへ引き継ぐ。
