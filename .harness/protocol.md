# 共通開発工程 v0.5.0

v0.7.0の任意累積品質は[cumulative-quality.md](cumulative-quality.md)を正本とする。既存工程と実行証跡を拡張し、REVIEW REQUIREDでもimplementationからreviewへ進める。enforceでは同じ分析対象の累積レビューが揃うまでdoneにできない。observeの所見を品質PASSと報告しない。

この仕様は、本プロジェクト独自の工程規約。Codex公式の必須ファイル形式ではない。
AIの実行、ツール、サンドボックス、承認はCodexが担当し、この基盤は成果物と工程移行を検証する。

v0.5.0の任意のPython構造品質契約は[構造品質ゲート](structural-quality.md)に定義する。既存工程を増やさず、discoveryのbaseline、再利用・影響範囲・構造レビュー、既存run/ciの実検査へ接続する。未有効の既存設定は保持する。

## 責務

| 担当 | 責務 |
| --- | --- |
| Codex | AIの実行とツール利用、実行環境の権限制御 |
| poteto-mode / common-workflow | 現在の工程を読み、プレイブックと専門スキルを使い、検証CLIで進行する |
| grill-me / grilling | 目的と制約の確認、観測可能な受入条件、未解決事項の整理 |
| ponytail | 方針、影響範囲、要件と検証の対応、最小の実装と修正 |
| ponytail-review | 別の作業コンテキストで意味的整合、設計、差分、検証内容を評価 |
| 検証CLI | 形式、参照、必要項目、実行結果、証跡の鮮度、工程順序を検証 |

スキルを差し替えても、工程と成果物の契約は変えない。AIが意味的に正しいと判断したことと、機械検証に通ったことを分けて記録する。

## 工程と完了条件

`discovery → requirements → design → implementation → review → done`

| 現在の工程 | 成果物 | 次へ進む条件 |
| --- | --- | --- |
| discovery | discovery.json | 目的・現状・制約を記載し、未解決質問がゼロ。既存変更は現状の根拠を記載 |
| requirements | requirements.json | 一意な要件ID、説明、受入条件が各要件に存在 |
| design | design.json | 方針・影響範囲・回復手順を記載し、全要件を変更予定パスと登録済み検証コマンドに対応づける |
| implementation | implementation.json + 自動実行証跡 | 実装者、実在する変更パス、要件に対応した全検証の成功。コード・成果物・コマンドが実行時から変わっていない |
| review | review.json | 実装者と異なるレビュアーとコンテキスト、全要件の確認、現在のコードと成果物に対するレビュー、未解決の重大指摘ゼロ |
| done | state.json / events.jsonl | 前工程すべての条件を維持。次の変更は新しい変更単位として開始 |

各変更単位を `.harness/changes/<id>/` に置く。`new` は新規開発、`change` は既存システム変更。どちらも同じ工程を使い、調査の内容と影響範囲を変える。
次工程の空テンプレートは移行時に作成する。テンプレートの存在だけで完了にはしない。

## 原指示と目的の契約（0.6.1）

ユーザーの指示を抽象化して本質的要求を理解し、最も直接的で最小十分な解決策へ具体化して実行する。抽象化は目的・問題の構造を正確にする作業であり、コードの抽象層を増やす作業ではない。確定要求・制約・指定された変更範囲を推測で置き換えない。

工程は増やさない。構想の曖昧さはdiscoveryのopen_questionsで扱い、確定した指示はその範囲で進める。簡単な変更は1つの原指示項目と1つの要件で足りる。6種類への分類や長文の要求分析を毎回出力する必要はない。

| 工程 | 既存成果物への接続 |
| --- | --- |
| discovery | requestへ今回の元指示を省略せず保存する。goalに目的、current_behaviorに現状の問題、constraintsに変更不能条件を記録する。構想段階は問題・期待結果を調べ、未確定手段の有力案を比較する。具体的な確定指示を一般化して再設計へ戻さない |
| requirements | request_itemsに原文の引用を置き、要求・制約と仮説・候補手段・例示を区別する。受入条件を持つ既存要件のsourcesで確定条件を全てカバーする。例示からの一般化でも固有の条件を保持する |
| design | 既存approach・decisions・impact_paths・traceabilityへ、実在する仕様・API・ライブラリ・再利用資産、責務・データ・状態・依存・変更範囲と検証を展開する。構造品質が有効なら既存reuse_candidates等を再利用する |
| implementation | 確定した要求・設計の範囲を実装し、既存checks/runで動作を確認する。不動作は仕様・再現・原因・基礎的な前提の順で調べ、複雑な迂回を足す前に見落としを除く |
| review | goalの達成とrequest全体の充足を別々に判定する。要求分解の漏れ・誤分類も原文と照合し、最小十分性・過不足・より単純な既存解を評価する |

request_itemsの各要素は、重複しないid、requestに実在する原文引用text、kind、真偽値bindingを持つ。kindはpurpose/problem/requirement/constraint/means/example/hypothesis。これは要求の性質であり、新しい成熟度分類ではない。必要な種類だけ使う。確定要求・制約はbinding=true、提案・仮説はfalseとし、指定手段や例示の条件が確定している場合もtrueで保護する。AIの推論はassumptionsへ理由を記載する。要求を変える発見は元要求との関係・根拠を示し、本人の新しい指示なしに確定要求を変更しない。

各要件のsourcesはrequest_itemsのidの非空配列であり、少なくとも1つの確定項目を参照する。全binding項目を要件へ対応づける。仮説の引用だけを根拠に確定要件を作らない。既存traceabilityが要件から変更パス・check IDへの対応を受け持つため、別の追跡表は作らない。

review.intent_reviewは次の形で、目的、原指示項目ごとの照合、最小十分性を記録する。各statusはpassed/failed/unverified、evidenceはコード・テスト・観測等の具体的な根拠。完了ゲートは全てpassedかつ非空の根拠を要求する。非確定の手段や仮説は、採用を強制せず採否の妥当性を確認する。構造レビューを実施済みの項目は、その根拠を参照してよい。

```json
{"purpose": {"status": "passed", "evidence": "目的を確認した操作・結果"},
 "sources": [{"source": "SRC-001", "status": "passed", "evidence": "原文条件を満たす差分・検証結果"}],
 "minimality": {"status": "passed", "evidence": "既存資産の調査と最小変更を選んだ理由"}}
```

0.6.1以降のnewがstateへintent_contract=1を記録し、テンプレートと既存check/advance/run/ciへ接続する。request・対応・レビューの変更には既存の承認ハッシュと指紋失効、reopen・再検証が適用される。フラグのない過去変更は旧形式で継続でき、更新で既存成果物・設定を改変しない。新しい原則の判断手順は旧変更にも適用できるが、未記録の契約を機械検証済みとは報告しない。フラグを手で削除して新しい変更のゲートを回避しない。

CLIが保証するのは原文引用・ID・対応の網羅、根拠欄、判定・証跡の有効性である。引用していない条件の発見、bindingの意味的妥当性、目的の正しさ、解の単純性、根拠の十分性は独立したAI・人のレビューが判断する。文字列を埋めたことだけで振る舞いを保証しない。AGENTSやSkillは書き込みを遮断するHookではなく、既存CIの完了ゲートへつなぐ。

## 検証と証跡

コマンドは `.harness/project.json` の `checks` に `id`・`argv`・`timeout_seconds` で登録する。
`run` はプロジェクトルートでargvを直接実行する。シェルの解釈は行わず、失敗・タイムアウトで停止する。
`run` 前後のプロジェクト指紋が同一であることを要求する。自動修正を伴うコマンドは先に実行し、修正しない検証を登録する。
標準出力・標準エラー、終了コード、時刻、コマンド、開始時からの変更パス、ソースと成果物の指紋を記録する。
開始時のファイル指紋と比較し、実際の変更パスが実装成果物に記録されていることを要求する。
アプリの変更パス判定からは、共通基盤が所有するファイルと導入先AGENTS指示を除く。これらの内容は検証・レビューの指紋に含めるため、共通版の更新後は再検証が必要になる。
検証ログに秘密情報を出すコマンドを登録しない。

Gitがある場合は追跡済み＋未追跡かつignore対象外のファイルを指紋に含める。Gitがない場合は通常のファイルを探索する。
`.git`、キャッシュ、変更単位の証跡は除外する。追加除外はproject.jsonに明記し、テスト対象のソースは除外しない。
シンボリックリンクはリンク先文字列と、プロジェクト内にある参照先の内容を指紋に含める。プロジェクト外へのリンクは拒否する。
検証コマンドの変更やコード変更で古い成功証跡は失効する。レビュー後のコード・上流成果物変更も失効する。
上流成果物の修正は `reopen <工程> --reason ...` で戻し、再検証する。

`check` は現在までのゲートを再検証する。`ci` は指定変更のdoneを要求し、全ゲートと登録検証をそのCI実行内で確認する。
過去のdone変更は、その時点の記録としてGitに保存する。別の変更でコードが変わった後、全過去変更の証跡が現在コードに有効であることは要求しない。
`ci` は対象変更IDを明示する。複数の変更を同時に進める場合も、同じ作業ツリーの変更で指紋が失効する。

## 配布・更新

成果物のGit保存は、品質ゲートのdoneとは別にrules.mdの保存契約で確認する。`backup-check`はpush先の実ブランチとローカルHEADを照合する。途中成果物も作業ブランチへ保存し、ローカルコミットだけをリモート保存済みと扱わない。

Gitタグ/コミットで配布版を固定し、導入時にVERSIONと共通ファイルのSHA-256を `.harness/framework.lock.json` に記録する。
ランタイム、共通指示、工程仕様、共通スキルをリポジトリへコピーする。クラウドとローカルはその同じコピーを使う。
各プロジェクトの検証コマンドとスキル割当はproject.json、工程成果物はchangesに所有する。
共通ファイルは各プロジェクトで直接改変せず、元の共通リポジトリで改善して版を更新する。
更新は `install.py --update-from <現在の版>` で明示する。自動追従しない。改変済みの共通ファイルは更新を拒否する。
既存のAGENTS.mdは内容を保持し、管理ブロックを追記する。AGENTS.override.mdがある場合はそこに追記する。
0.1.0からの更新では、以前の標準のスキル割当を実スキルへ移行し、独自の割当と検証コマンドを保持する。
実スキルの原本は配布元コミットとGit blob SHA・SHA-256で固定し、上流ライセンスと導入先のprovenanceを同梱する。

## v0.5.0の任意UI契約

UI専門判断はui_design担当から既存の設計・実装・独立レビューへ接続する。工程順序と一般的な受入条件は変えない。詳細なプロジェクト設定、Registry、設計とレビュー、providerの形式はui-design.mdを正本とする。

ui設定を有効にした対象では、設計ゲートが意味→部品・表現→画面シナリオの対応を検査する。共有定義の変更はsharedとして扱い、変更前の指紋と承認された変更予定を分ける。既存画面のbefore画像は実装前に既存ブラウザ手段で取得し、prepareで記録する。

runは既存checkへ変更ID・check ID・実行ごとの証跡ディレクトリを環境変数で渡す。UI providerの報告・画像等を既存receiptへ結び付ける。コード・工程成果物・コマンド・添付の変更や欠落で証跡は失効する。実行中に設計や基準画像を更新しない。レビューはlatest.jsonでなく特定の不変receiptを参照し、CI再実行でレビュー対象画像を置き換えない。

observeは品質上の失敗・未確認を結果に残して接続を観測する。enforceではUI検証と独立した実画面レビューのpassedを完了条件に加える。構造不正・証跡改変・検証プロセスの非0終了とtimeoutはobserveでも拒否する。未設定の旧プロジェクトの契約は維持する。

## 初期版の保証範囲

v0.7.0ではui schema_version=2を追加する。新規UI作業は[ui-principles.md](ui-principles.md)に従い、10原則の制作判断、型付き期待値、同じscenarioの添付から取得した実測値、原則別独立レビューを検査する。v2のui設定と参照check定義はnewで固定する。既存v1・未設定の契約を自動変更せず、原則検証への未接続を成功と報告しない。

CLIは工程の形式的条件を検証する。要件文の正しさ、テストの十分さ、レビュアーが独立した実在人物であることは自動で証明できない。
レビューIDとコンテキストIDは申告された識別子。独立レビューは別コンテキストのエージェント、別セッションのCodex、または別の人が実施する。
ファイルと指紋は誤操作・古い証跡の検出用。署名付き監査台帳や、悪意あるエージェントへのセキュリティ境界ではない。
AGENTS.mdとスキルは指示であり、全ファイル書き込みを強制的に遮断するフックではない。強いマージ制御にはCIを必須チェックに設定する。
プラグインはスキルの配布用。クラウドでのスクリプト配置はリポジトリ側の導入で行う。

## v0.4.0の個人設定と自律配送

環境の `codexenvset/profile.json` は利用者所有とし、共通バンドルの管理対象から分ける。schema_versionは1、modelはinherit-parent、principlesは本人が明示した判断基準の文字列配列、autonomyはcompletion、branch_prefix、base_branchを持つ。標準completionはreviewであり、配布しただけで自動マージ権限を付与しない。

環境導入時の `--profile` は初回だけ取り込む。既存の異なる個人設定への上書きを拒否する。bootstrapは新規対象のproject.jsonへautonomyだけを渡し、私的なprinciplesはコピーしない。既存の版・設定・成果物は保持する。明示更新でprofileを指定した場合も既存autonomyを上書きしない。

project.jsonの任意のautonomyは、completionがreview/pr/merged、branch_prefixがai/などの接頭辞、base_branchがdefaultまたは具体的なブランチ名である。reviewは既存と同じ品質完了、prはPR作成、mergedは条件付きマージを完了地点とする。個人設定や現在の依頼より広い権限をAI自身が設定しない。

品質工程のdoneは変更しない。配送状態は `.harness/changes/<id>/delivery.json` に置き、品質指紋の対象外とする。実PRが配送状態の正本である。記録だけで未実施の配送を完了にしない。

`ship-check` は書き込みやPR作成をしない。doneと全品質ゲート、コミット済みコードとの一致、AI用ブランチ、実PRのhead・base、レビュー対象base_sha、CI・レビュー・保護条件、許可されたマージ方式を確認する。レビューの品質指紋はコード・設定の内容に結びつける。工程証跡だけを後からコミットする場合も、コードの指紋が一致することを要求する。

配送する変更のreview.jsonにはbase_shaを追加する。最新のマージ先SHAと一致し、そのbaseが作業HEADの祖先である必要がある。baseやコードが変われば品質工程をreopenし、再検証・独立レビューを行う。配送直前に取得した実PRのheadをexpected_head_shaとしてGitHubへ渡す。最終的なブランチ保護の強制はGitHubが担当する。

`ship` はpush済みブランチから一回分を実行する。既存PRを全状態で照合し、なければ作成する。待機条件はwaitingとして保存し、条件が整えばSHAを指定してマージする。マージ応答が失われても次回の実PR照合で復元し、同じPRを重複作成しない。強制push・保護ルール変更・必須レビューの代行承認・常駐実行は行わない。

v0.9.0は任意のui schema_version=3を追加する。v2の工程を再利用し、見えるcontrolと実起動領域の幅・高さ・action、全copyの目的と出典・代替・重複理由、励まし等の文言指定または明示的な制作委任、期待値自体の独立reviewを検査する。v3もnew時に固定し、3から2への降格を許さない。既存v1/v2と独自checkはinstallerで変更しない。
