# 構造品質ハーネスの評価手順

## 機械的な正しさ

検査用環境で`QUALITY_NATIVE_TESTS=1 python -m unittest discover -s tests -v`を実行する。native接続試験をskipした実行と区別する。
fixtureのレビューは合否契約を試す架空データであり、独立AIレビューの実績ではない。
新規clone、3個目、別cloneへの入替、循環の維持・拡大・改名、既存境界負債、解析漏れ、古い証跡、CI再比較を別に確認する。
その後、固定したGit基準に対して`runtime/structure.py scan --config quality.json --base BASE_SHA`を実行する。実ツール出力と所要時間を保存し、初回ダウンロード時間を分ける。

## AI開発への効果

同じ開始コード・要求・モデル設定・作業予算を使い、現行構成と新構成を別セッションで比較する。各組の開始SHA、設定、プロンプト、終了時の差分、実行ログを保存する。

| 試行 | 要求の条件 | 重点確認 |
| --- | --- | --- |
| 1 | 共通関数を再利用できる機能追加 | 妥当な既存資産の発見・採用 |
| 2 | 別名の同等機能が存在する要求 | 意味的重複、不自然な流用 |
| 3 | 呼び出し元に影響するAPI変更 | 影響範囲と関連テストの見落とし |
| 4 | 新規モジュールが妥当な変更 | 責務分離と新設理由 |
| 5 | 循環・レイヤー違反を誘発する変更 | 新規違反と既存負債の拡大 |
| 6 | 回避策を積み重ねやすい修正 | 前提の再検討、不要な抽象化・分岐 |

条件を伏せたレビューで、意味的重複、責務混在、不要なラッパー、別箇所への負債の移動、見落とした呼び出し元を根拠付きで数える。native clone候補数とは別の指標にする。
人の介入回数・手直し量・誤検出対応時間、検査とレビューを含む経過時間・トークン・CPU・最大メモリーを記録する。小標本で統計的効果を断定しない。

各試行は「開始SHA／条件／結果差分／検査ログ／匿名レビュー／時間・トークン／介入／限界」を1組として保存する。検査未実施をゼロ件として集計しない。
初期の速度目標はこの基盤で15秒以内だが、品質の合否基準にはしない。

探索の遅さ・読み直し・影響範囲の見落としが残った場合にだけ、Codebase Memory MCPを単独で比較する。探索コストが減っても正答性が悪化したら採用しない。Hooks・他言語・GUIはこの比較の前提にしない。

## 累積品質の後続比較（未実施）

各ケースを独立したGitリポジトリにし、初期SHA・コミット列・要求・責務の正解・期待判定を固定する。従来の差分検査、既存nativeツールのみ、v0.8.0の累積評価を同じ列へ実行する。ランナー/設定/ログ/所要時間を保存し、検出できないケースも失敗として残す。AIを含む比較は同条件の別セッションで行う。

| ケース | 固定する操作 | 比較する期待結果 |
| --- | --- | --- |
| A | 同じ責務へ10コミットで分岐と依存を追加 | 差分ごとは小さくてもREVIEWを起動 |
| B | 同じ責務へ10コミットの小修正、構造一定 | 回数だけで不要な整理を要求しない |
| C | 宣言した責務と異なる処理を段階的に配置 | 境界違反の検出と意味的レビューの見逃し率 |
| D | 同じ根因IDに3回の回避処理、終了条件を記録 | 履歴を参照して根因・限定整理を評価 |
| E | 挙動検証を維持し、責務に沿って分割 | 行数増を理由にBLOCKせず改善として説明 |
| F | 各回の増加は閾値未満で長期anchorから乖離 | 長期基準からREVIEWを起動 |
| G | 導入時のclone/循環を維持、拡大、解消、再発 | 維持と新規悪化を区別。未観測の再発は断定しない |
| H | epoch承認、rename/分割、shallow/欠落SHA | 比較可能性を保持し、欠測は合格にしない |
| I | 同じ入力を既存jscpd/Tach/NetworkXへ実行 | native再利用と独自解析の重複がないこと |
| J | 重複した解析/MCP構成と最小構成を比較 | 精度・待ち時間・導入保守費から不要な構成を除外 |

機械回帰の入口は`tests/test_quality_history.py`、`test_quality_gate.py`、`test_structure_native.py`、`test_policy.py`。これはAIの意味理解・独立性や本番での効果を証明する比較ではない。REVIEW/BLOCKの適合率・再現率、不要なリファクタ要求、根因の見逃し、レビュー介入時間、トークンとnative実行時間を別々に集計してから閾値とenforce移行を判断する。
