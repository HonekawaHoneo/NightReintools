# 調査と要件

AGENTSと `.harness/protocol.md`、対象変更のstate.jsonを読む。
既存変更は関連コード・利用者の操作・テスト・既存仕様を読み、実際の現状と根拠をdiscovery.jsonへ記録する。
新規開発は現状を「未実装」などの事実として記録する。

protocol.mdの「原指示と目的の契約」を使う。discovery.requestへ元の指示を残し、目的・問題・要求・制約・手段・例示を必要な範囲で区別する。目的はgoal、障害はcurrent_behavior、未確定の推論はassumptionsへ接続し、同じ分析を複製しない。
構想段階は解決したい問題と期待結果を掘り下げ、実現手段が未定なら有力案の利点・欠点・制約を比較する。確定した具体指示はその範囲で理解し、再設計を強制しない。

目的を変える不足情報を少数の質問にまとめ、質問に依存しない調査を進める。選択肢を示すときは影響を説明する。
既存のユーザー回答を優先し、確認済みの決定を再度承認待ちにしない。
未解決事項を解決するまでdiscoveryを完了させない。

requirements.jsonでは各要件に一意なID、利用者から見た挙動、具体的な受入条件を記載する。
request_itemsで原文引用と確定条件（binding）を保持し、要件のsourcesへ結ぶ。仮説・候補手段を確定要求と扱わず、例示が持つ具体条件も落とさない。指定手段が確定条件なら保護する。本質的問題の発見は元要求との関係・根拠を示し、目的を推測で置き換えない。確定要求の変更は本人の新しい指示が必要。
既存変更は維持する振る舞いと回帰条件も要件に含める。推測による要求はassumptionsに理由を記載する。
範囲外はout_of_scopeに記録する。設計の手順・実装済みの結果を要求として混ぜない。
成果物作成後はCLIのadvanceで検証する。
